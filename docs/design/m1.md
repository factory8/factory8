# M1 technical design

**Status:** proposals, not yet agreed. Task 1.D in `docs/plans/poc-wbs.md` turns each one into a decision with the user. Then each section records the decision, why it was made, the rejected alternative, and anything still open.

M1 means: `f8 run <issue>` → a one-step workflow → a sandbox built from the repo's Nix dev shell → Claude Code through the adapter and LiteLLM → a draft PR (PRD §8). The contracts are in `specs/phase0-contracts.md`.

## D1. The workflow

**Proposal:**
- **Shape:** one workflow, `runWorkflow({ runId, issue, repo, prompt, profile })`, on task queue `factory8`. The workflow ID is the run ID.
- **Activities:**
  1. `createSandbox`
  2. `startStep` (POST /steps)
  3. `pollStep` (long-polls `GET /steps/{id}/events` until an exit event)
  4. `openDraftPR`
  5. `deleteSandbox`, in a `finally` block
- **M1 settings:**
  - `pollStep` gets a long start-to-close timeout (about 2 h); heartbeats come in M2 (2.2).
  - One attempt and no retries; retries come in M4.
  - On `needs_input`, M1 fails the run, because M3 adds the wait.
- **Naming:**
  - The run ID is a short random ID.
  - The branch is `f8/<runId>`.
  - The step ID is `${runId}.build.1` (spec §1.2).

**Open:** whether the run ID should include the issue number.

## D2. Sandboxes on Kubernetes

**Proposal:**
- **How the worker creates one:** through `@kubernetes/client-node`, with a ServiceAccount and a Role limited to the sandbox namespace (create, get and delete on `Sandbox`, or on `SandboxClaim` if the extensions are installed).
- **The template:** a `SandboxTemplate` per project, using the Kata RuntimeClass and the project image.
  - The adapter is the container's main process, on port 7070.
  - A volumeClaimTemplate mounts an NFS PVC at `/f8` (about 10Gi).
  - The Secret from spec §5 is provided as env.
- **Readiness:** the worker waits for the Sandbox to be Ready, then reaches the adapter through whatever address agent-sandbox provides (see the facts table).
- **Namespaces:** `factory8` for Temporal, Postgres and the worker; `f8-sandboxes` for the sandboxes.

## D3. The project image (A14)

**Proposal:**
- **Build:** `pkgs.dockerTools.streamLayeredImage`. It's in nixpkgs, so it needs no extra flake input.
- **Contents:**
  - the dev shell's packages (`packages` and `nativeBuildInputs`, gathered with `buildEnv`);
  - claude-code (from nixpkgs, if it isn't too far behind upstream);
  - git and gh;
  - Node, to run the adapter;
  - the adapter and `f8-ask`.
- **Known loss:** a dev shell's `shellHook` isn't carried into the image. Accept that for M1.
- **Where it's defined:** the factory8 flake exposes a function such as `lib.sandboxImage { pkgs, shell }`, so the same function later builds the image for `librepod/marketplace`, whose environment is a `shell.nix`.
- **Delivery:** built by hand on the laptop and loaded onto the single node with `k3s ctr images import`. No registry yet; the SBX-17 build workflow is Phase 1.

**Rejected:** nix2container, which needs an extra flake input.

## D4. Deployment

**Proposal:**
- **Manifests:** plain YAML in `deploy/`, applied with `kubectl apply -k` (kustomize is built into kubectl).
- **Postgres:** a StatefulSet on the official postgres image, used only by Temporal.
- **Temporal:** one server deployment. The `auto-setup` image is a candidate because it sets up the schema itself. Add the UI if it's cheap.
- **Worker:** an image built with Nix (Node + the worker code), imported with `ctr` like the project image, running as a Deployment.

**Rejected:** the official Temporal Helm chart, which is too heavy for the POC.

## D5. `f8 run <issue>`

**Proposal:**
- **Where:** the `cli/` workspace, running on the user's laptop.
- **What it does:**
  1. Reads the issue with `gh issue view <n> --json title,body`.
  2. Builds the prompt from the issue's title and body.
  3. Starts `runWorkflow` and waits for the result.
  4. Prints the draft PR URL.
- **Reaching Temporal:** at `TEMPORAL_ADDRESS`, by default `localhost:7233`, through a `kubectl port-forward` that the user runs.
- **The repo:** comes from the `origin` remote of the current directory.

## D6. The draft PR

**Proposal:**
- **How:** the `openDraftPR` activity calls GitHub's REST API with `fetch` (`POST /repos/{owner}/{repo}/pulls`, `draft: true`) using `GH_TOKEN`, which the worker gets from the same Secret.
- **Title:** the issue's title.
- **Body:** the agent's summary, `Run: <runId>`, and `Fixes #<n>`, so merging the PR closes the issue.

**Rejected:** Octokit, a dependency for a single call.

## D7. Code layout and tests

**Proposal:**
- **Workspaces:** `adapter/`, `worker/` (workflow, activities, worker main) and `cli/`.
- **Shared types:** move `StepRequest` and `StepEvent` into `adapter/src/types.ts`; the worker imports them with `import type`.
- **Tests:** workflow tests use `@temporalio/testing` (TestWorkflowEnvironment) with mocked activities. The first real run (1.8) is the end-to-end test.

**Rejected:** a separate contracts package.

## D8. Installation settings

**Proposal:**
- **Worker:** env vars on its Deployment, such as the default model and the sandbox namespace and template. No config file and no `project.yaml`.
- **Sandbox:** LiteLLM's URL and key come from the Secret (spec §5).
